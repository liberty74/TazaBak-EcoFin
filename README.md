# TazaBAK EcoFin

Smart City & GreenTech MVP для управления отходами в Кокшетау — платформа
Future Minds Hackathon 2026, трек **EcoFin**.

## О разработке — что было до хакатона и что делается сейчас

Команда развивает свою предыдущую разработку — платформу мониторинга
контейнерных площадок, созданную в начале августа 2026 года.

Разрешение на развитие собственной предыдущей разработки как основы для
проекта на треке EcoFin получено от Оргкомитета Future Minds Hackathon 2026.

В этом репозитории:

- **Базовые коммиты `base(backend)`, `base(frontend)`, `base(iot)`** — перенос
  существующей платформы: FastAPI backend, React/Vite frontend, прошивка ESP32.
  Это стартовая точка.
- **Все коммиты после базовых** — новый экономический слой EcoFin, разработанный
  в период онлайн-этапа хакатона (15–25 августа 2026): расчёт сэкономленных
  рейсов, топлива, денег и CO₂, прогноз заполнения контейнеров, планировщик
  маршрута, кабинет малого бизнеса и AI-рекомендации на посчитанных метриках.

## Что умеет MVP

- роли `user`, `volunteer`, `dispatcher`;
- регистрация и вход пользователей;
- PostgreSQL + SQLAlchemy с автоматическим созданием таблиц (SQLite остаётся
  запасным вариантом для быстрой локальной разработки);
- идемпотентный seed демо-данных;
- анализ фото хлеба через CLIP zero-shot с вероятностями по классам;
- статусы `approve`, `reject`, `invalid`;
- QR-префиксы `GOOD`, `BAD`, `NONE`;
- начисление и списание баллов через единый ledger;
- магазин и процедурная генерация Eco-NFT в SVG;
- волонтёрские задания и подтверждение выполнения диспетчером;
- карта контейнеров;
- телеметрия ESP32;
- EMA-фильтр заполненности;
- FireScore и алерт `FIRE_RISK`;
- детекция `ILLEGAL_DUMP` реальным YOLOv8 — и по кадру ESP32-CAM, и по загруженному;
- WebSocket-команды `OPEN_LID` и `CLOSE_LID`;
- диспетчерская панель;
- экран «Экономия»: деньги и CO₂ крупно, график по неделям, раскрытие формулы;
- кабинет пекарни: ввод списаний и прогноз остатков на завтра;
- AI-помощник Баки с Gemini и offline fallback;
- grounded-рекомендации на посчитанных метриках с проверкой чисел;
- симулятор телеметрии и анализа хлеба.

## Запуск в Docker

Весь стенд одной командой:

```bash
docker compose up --build
```

| Адрес | Что |
|---|---|
| http://localhost:5173 | интерфейс |
| http://localhost:8000/docs | Swagger |

Первая сборка долгая: ставится `torch` и **в образ запекаются веса** YOLOv8 и
CLIP. Это сделано намеренно — иначе первый запрос на защите уходит качать
около 600 МБ с Hugging Face и выглядит как зависшее приложение. После сборки
контейнер работает без интернета: советы Баки без ключа Gemini собираются
локальными правилами по тем же посчитанным числам.

База живёт в отдельном сервисе `db` (PostgreSQL 16) и в томе `tazabak-postgres`,
а не в слое образа: пересборка не должна стирать историю вывозов, на которой
считается вся экономика.

Ключ диспетчера и ключ Gemini передаются через окружение и в образ не
попадают:

```bash
DISPATCHER_API_KEY=свой-ключ GEMINI_API_KEY=свой-ключ docker compose up --build
```

## Развёртывание в облаке

`render.yaml` поднимает три бесплатных сервиса Render: PostgreSQL 16, API и
витрину. Blueprints → New Blueprint Instance → этот репозиторий → Apply.

CLIP и YOLOv8 вместе занимают около 700 МБ оперативной памяти, а бесплатный
инстанс даёт 512 МБ, поэтому локально в облаке они не считаются. Разбор фото
хлеба там идёт через Gemini по сети — кнопка живая. Где CLIP установлен, в сеть
не ходят вовсе. Каким движком посчитан вердикт, написано прямо под
вероятностями; режим приходит из `/health` полем `image_analysis`.

Подробности, включая то, что бесплатный инстанс засыпает после 15 минут без
запросов: [docs/DEPLOY.md](docs/DEPLOY.md).

## Сценарий сдачи хлеба

Frontend отправляет multipart-запрос:

```text
POST /api/bio/analyze
file=<image>
user_id=123
device_id=bio-demo-001
idempotency_key=<unique-key>
```

Backend:

1. проверяет пользователя и устройство;
2. сохраняет и валидирует изображение;
3. запускает CLIP zero-shot;
4. сравнивает фото с тремя текстовыми описаниями;
5. сохраняет `BioAnalysis` вместе с вероятностями;
6. начисляет 15 баллов при `approve`;
7. создаёт `OPEN_LID`;
8. отправляет команду через WebSocket.

Результаты:

```text
approve — свежий хлеб, пригоден
reject  — обнаружена плесень
invalid — хлеба нет в кадре либо модель не уверена
```

Коды имеют уникальный префикс:

```text
GOOD...... — approve, 15 баллов
BAD.......  — reject, 0 баллов
NONE...... — invalid, 0 баллов
```

## Сценарий муниципального контейнера

ESP32 отправляет:

```json
{
  "device_id": "municipal-prototype-001",
  "distance": 45,
  "temp_in": 24,
  "temp_out": 21
}
```

Endpoint `/api/sensors/ingest`:

1. сохраняет измерение;
2. рассчитывает заполненность для физического бака высотой 25 см;
3. считает `0%` при расстоянии `25 см` и `100%` при `7 см`;
4. применяет EMA с `alpha=0.3` между физическими границами;
5. сохраняет FireScore как диагностическую метрику;
6. при температуре единственного DS18B20 **строго выше 50°C** сразу создаёт `FIRE_RISK`;
7. создаёт `CLOSE_LID`;
8. отправляет команду подключённому устройству по WebSocket.

Формулы:

```text
raw_fill = (25 - distance) / (25 - 7) * 100

EMA = 0.3 * current_raw + 0.7 * previous_ema

FireScore = 0.7 * (temp_in - temp_out)
          + 0.3 * delta_rate

FIRE_RISK = temp_in > 50°C
```

`temp_out` сохраняется для совместимости и диагностического FireScore, но не
участвует в принятии пожарного решения для текущего макета с одним DS18B20.

## Экономическая модель EcoFin

Отчёт отвечает на вопрос трека: сколько денег и ресурсов сэкономлено.

### Как определяется вывоз

Мусор накапливается постепенно, поэтому резкое падение уровня между двумя
замерами может означать только одно — приезжал мусоровоз. Событие
`CollectionEvent` создаётся автоматически из телеметрии, когда сырой уровень
падает с 45 % и выше до 15 % и ниже. Используется именно сырой уровень, а не
EMA: сглаживание как раз и создано, чтобы гасить такие скачки.

Записывается уровень **до** вывоза — тот, который видел диспетчер. Он и решает,
был ли рейс оправдан.

### Формулы

Модель маржинальная. Мусоровоз объезжает много площадок за один маршрут,
поэтому пропущенная площадка экономит не рейс от базы, а плечо до следующей
точки и время бригады на этой точке. Считать целый рейс на один контейнер —
завысить результат в разы, и первый же вопрос жюри сломает такое число.

```text
Стоимость одного обслуживания площадки:
  литры  = km_per_stop / 100 * fuel_consumption_l_per_100km
  ₸_топл = литры * fuel_price_kzt_per_liter
  ₸_бриг = minutes_per_stop / 60 * crew_cost_kzt_per_hour

Экономия за период:
  N_график = дней / 7 * baseline_trips_per_week * контейнеров
  N_факт   = число CollectionEvent за период
  ΔN       = max(0, N_график − N_факт)

  км      = ΔN * km_per_stop
  литры   = ΔN * литры_на_обслуживание
  ₸       = ΔN * (₸_топл + ₸_бриг)
  CO2, кг = литры * co2_kg_per_liter
```

Обслуживание чаще графика — это не отрицательная экономия, а её отсутствие,
поэтому `ΔN` не опускается ниже нуля.

Окупаемость считается после вычитания подписки, потому что для клиента она
расход:

```text
экономия_в_месяц = ₸ / дней * 30
чистая_экономия  = экономия_в_месяц − подписка * контейнеров
окупаемость      = установка * контейнеров / чистая_экономия
```

Если чистая экономия не положительна, срок окупаемости не определён — поле
возвращает `null`, а не бесконечность.

### Откуда взялся тариф

Тариф выведен из расчёта, а не назначен.

Один заезд на площадку обходится оператору в **379 ₸**: 0,39 л дизеля — 129 ₸,
шесть минут работы бригады — 250 ₸. На десяти контейнерах пилота действующий
график даёт 150 заездов в месяц, а вывоз по фактической заполненности — 92.
Разница в 58 заездов и есть экономия: **21 987 ₸ в месяц**, или около
**2 200 ₸ на контейнер**.

**Подписка 1 000 ₸** — 45% этой суммы. Клиент оставляет себе примерно 1 200 ₸
на бак каждый месяц; если бы платформа забирала всю экономию, покупать её не
имело бы смысла. Ранее в проекте стояли 5 000 ₸ — вдвое больше всей создаваемой
экономии, из-за чего чистая экономия оператора была отрицательной, а срок
окупаемости не определялся. Это была ошибка назначения цены, а не расчёта.

На пилоте это даёт: установка 28 000 × 10 = 280 000 ₸, чистая экономия
11 987 ₸ в месяц, **окупаемость 23 месяца**.

**Установка 28 000 ₸** — комплектующие и монтаж одного бака:

| Позиция | ₸ |
|---|---|
| ESP32 DevKit | 2 500 |
| Ультразвуковой датчик HC-SR04 | 800 |
| Датчик температуры DS18B20 | 1 000 |
| Привод заслонки SG90 | 1 200 |
| Корпус, крепёж, проводка | 3 000 |
| Питание: аккумулятор и солнечная панель | 8 000 |
| Монтаж и пусконаладка | 5 000 |
| **Себестоимость** | **21 500** |
| Гарантия и запас на брак | 6 500 |
| **Цена для клиента** | **28 000** |

Все параметры меняются через `PUT /api/eco/profile` без переразвёртывания.
Ответ `GET /api/eco/savings` содержит блок `formula` со всеми входными
значениями, поэтому любое число на экране раскрывается до исходных данных.

### Прогноз заполнения

Алерт сообщает, что уже случилось. Прогноз сообщает, что ехать пока не нужно —
и именно это экономит деньги, поэтому «AI-рекомендация по оптимизации» из
кейс-брифинга берётся отсюда.

По замерам текущего цикла наполнения строится линейная регрессия методом
наименьших квадратов:

```text
b = Σ(t − t̄)(y − ȳ) / Σ(t − t̄)²        скорость наполнения, % в час
a = ȳ − b · t̄
R² = 1 − Σ(y − (a + b·t))² / Σ(y − ȳ)²   насколько прямая объясняет данные
ETA = (порог − текущий уровень) / b      часов до вывоза
```

МНК написан вручную: это три строки арифметики, они не тянут зависимость и
воспроизводятся на доске во время защиты. `R²` показывается диспетчеру, чтобы
он видел, насколько тренду можно верить.

Три защиты от ложного прогноза:

- **Замеры до последнего вывоза не участвуют.** Через момент опорожнения
  наклон стал бы отрицательным, а прогноз — бесконечным.
- **Минимум три замера.** Через две точки всегда проходит идеальная прямая,
  и шум выглядел бы уверенным трендом.
- **Бак, который не наполняется, не получает срок.** Возвращается
  `not_filling`, а не огромное, но правдоподобное число.

### Планировщик маршрута

`GET /api/eco/route` отвечает двумя числами рядом: длина объезда всех площадок
и длина объезда только тех, что подходят к порогу в пределах горизонта.
Расстояния — по формуле гаверсинуса:

```text
a = sin²(Δφ/2) + cos φ₁ · cos φ₂ · sin²(Δλ/2)
d = 2R · arcsin(√a),   R = 6371 км
```

Маршрут строится жадно (ближайший сосед от автобазы), затем улучшается 2-opt:
переворот участка маршрута, пока это сокращает путь. Тур замкнутый — машина
возвращается на базу.

Прямая линия короче дороги, поэтому к расстоянию применяется коэффициент
извилистости 1,3. **Оба сценария считаются одним алгоритмом по одной модели
дорог** — иначе сравнение было бы подтасовкой.

### Кабинет пекарни

Пекарню не интересуют маршруты мусоровозов: её деньги утекают вечером, когда
списывается непроданная выпечка — ровно то, что сказали на интервью в Астане.

Спрос там недельный, а не дневной: вторник похож на прошлый вторник сильнее,
чем на вчера. Поэтому прогноз усредняет **тот же день недели** за последние
4 недели, а не скользящее окно по всем дням подряд. Если истории по этому дню
недели ещё нет, ответ честно помечается `basis: "all_days"`.

Стоимость спасённого продукта считается по цене каждой записи: багет и буханка
стоят по-разному. Это **не деньги, вернувшиеся пекарне** — продукт уже списан.
Поэтому сумма лежит отдельно от `money` и никогда к ней не прибавляется.

### Демонстрационные данные

Свежая база получает данные, без которых экраны открывались бы пустыми:

| Что | Объём | Пометка |
|---|---|---|
| Пилотные площадки Кокшетау | 9 точек | координаты ориентировочные |
| История обслуживания | 30 дней | `source="SEED"` |
| Замеры текущего цикла | 14 часов на площадку | нужны прогнозу |
| Списания пекарни | 4 недели | нужны недельному прогнозу |

События обслуживания от телеметрии пишутся с `source="SENSOR"`, поэтому
демо-данные невозможно спутать с измерениями.

**Физический прототип `municipal-prototype-001` намеренно исключён из сида
замеров** — во время демонстрации он присылает собственную настоящую
телеметрию, и синтетическая история её бы исказила.

## Экраны EcoFin

| Экран | Путь | Кому |
|---|---|---|
| Экономия | `/dispatcher` | коммунальной службе, акимату |
| Прогноз заполнения | `/dispatcher/forecast` | диспетчеру смены |
| Источники дохода | `/dispatcher/revenue` | инвестору, акимату |
| Кабинет пекарни | `/dispatcher/bakery` | малому бизнесу |
| IoT управление | `/dispatcher/devices` | технику на выезде |

Экран «Экономия» открывается **первым** после входа диспетчера: трек EcoFin
спрашивает, сколько денег и ресурсов сэкономлено, — отвечаем сразу.

Что на нём, сверху вниз: сэкономленные тенге и килограммы CO₂ крупно, четыре
плитки в постоянном порядке «рейсы → топливо → деньги → CO₂», график экономии
по неделям с таблицей-двойником, маршрут «объехать все / по плану»,
рекомендации Баки, спасённый хлеб **отдельной карточкой**, окупаемость и
раскрывающийся блок «Откуда цифра» с подставленными числами.

Последняя неделя периода почти всегда неполная. Она помечена и на графике
(полым кружком), и в таблице — иначе её меньшая высота читалась бы как обвал
экономии, хотя неделя просто ещё идёт.

На экране прогноза на шкале часов остаются только площадки с посчитанным
сроком. «Уже пора» — это ноль, а «прогноз недоступен» — вообще не число:
показывать их на одной оси с остальными значило бы соврать формой, поэтому
они вынесены отдельными блоками с указанием причины.

Экран доходов отделяет измеренный пилот от проекции на город: проекция идёт
пунктирной карточкой с меткой «расчёт, не факт» и не появляется, пока её не
запросили. У каждого источника рядом с суммой стоит основание вида
«10 баков × 1 000 ₸», чтобы число проверялось на экране, а не на слово.

Экран «IoT управление» показывает **только собранные баки**. В базе двенадцать
площадок, а плата пока собрана одна: остальные адреса нужны прогнозу и
маршруту, но открывать у них заслонку и смотреть камеру не у чего. Ряд карточек
с кнопками, за которыми нет железа, обещал бы жюри несуществующее.

## Где в проекте ИИ

Три места, и в каждом модель делает то, для чего она подходит.

### 1. Прогноз заполнения — линейная регрессия

Предсказание, а не реакция на событие: см. раздел «Прогноз заполнения» выше.
EMA и гаверсинус мы ИИ **не называем** — это математика.

### 2. Качество хлеба — CLIP zero-shot

`yolov8n.pt` обучена на COCO, где **нет ни класса «хлеб», ни класса
«плесень»**. Детектор объектов физически не может ответить на вопрос
«испорчен ли этот хлеб», поэтому решение принимает CLIP.

CLIP помещает изображения и текст в одно векторное пространство, поэтому фото
можно сравнить с письменным описанием того, что мы ищем:

```text
"a photo of fresh bread"        → approve
"a photo of bread with mold"    → reject
"a photo with no bread in it"   → invalid
```

Считается так:

```text
similarity = image_vector · text_vector        оба вектора единичной длины
logits     = similarity × exp(logit_scale)     собственная температура CLIP
p          = softmax(logits)                   вероятности, в сумме 1
```

На каждый класс берётся не одна фраза, а три и усредняется: одна формулировка
— это одна точка в пространстве, и она чувствительна к своей же случайной
редакции.

Вероятности возвращаются в ответе API и показываются пользователю. Если
уверенность ниже `CLIP_MIN_CONFIDENCE`, баллы **не начисляются**: балл — это
реальная ценность, а совет «этот хлеб можно отдать животным» — реальная
ответственность, поэтому на догадке их выдавать нельзя.

Датасет для этого не нужен — в этом и смысл zero-shot.

### 3. Рекомендации — grounded-LLM

`GET /api/eco/recommendations` отвечает тремя действиями на завтра.

Модель **не имеет доступа к базе и ничего не считает**. Все числа считают
движки EcoFin, складываются в JSON и передаются модели с инструкцией
использовать только их.

Это не оставлено на доверии. Каждое число из ответа модели сверяется с
числами, которые ей выдали: рекомендация, где встретилось постороннее число,
**отбрасывается и до диспетчера не доходит**. Тот же набор фактов
возвращается в поле `facts`, поэтому проверку можно повторить руками.

Если Gemini недоступен — нет ключа, квоты или сети — рекомендации собираются
детерминированными правилами по тем же числам. Меняется формулировка, но не
цифры.

Формулировка для защиты: **LLM у нас интерпретатор, а не источник фактов.**

## WebSocket ESP32

ESP32 подключается к:

```text
ws://<компьютер>:8000/ws/device/municipal-prototype-001
```

Backend может отправить:

```json
{"action":"CLOSE_LID","command_id":15}
```

или:

```json
{"action":"OPEN_LID","command_id":16}
```

В текущем MVP реестр подключённых устройств хранится в памяти одного процесса. Поэтому Uvicorn запускается с одним worker.

## ESP32-CAM

Кадр отправляется в:

```text
POST /api/vision/frame
```

Поток MJPEG можно сохранить через диспетчерский endpoint:

```text
PUT /api/dispatcher/devices/{device_id}/camera
```

```json
{
  "stream_url": "http://192.168.1.50:81/stream"
}
```

Frontend получает поток через:

```text
GET /api/cameras/{device_id}/stream
```

После сохранения MJPEG URL backend каждые 5 секунд:

1. получает JPEG через стандартный endpoint ESP32-CAM `/capture`;
2. запускает `yolov8n.pt`;
3. сохраняет размеченный кадр в `static/vision`;
4. создаёт или обновляет один открытый `ILLEGAL_DUMP` без спама дублями;
5. показывает кадр с рамками и классы объектов в окне «Камера ИИ».

Ручной анализ для презентации:

```text
POST /api/dispatcher/devices/{device_id}/camera/analyze
```

Последний обработанный кадр:

```text
GET /api/dispatcher/devices/{device_id}/camera/analysis
```

## Ограничения текущего MVP

- SQLite остаётся только как быстрый локальный вариант; рабочая конфигурация
  и `docker compose` используют PostgreSQL;
- WebSocket-реестр рассчитан на один Uvicorn worker;
- CLIP работает zero-shot, без дообучения на своём датасете: качество на
  редких видах порчи не замерено, свои метрики появятся только со своей
  размеченной выборкой;
- модели инференсятся на CPU, первый запрос после старта дольше остальных —
  в этот момент веса загружаются в память;
- QR-коды генерируются с уникальным префиксом и случайным числовым суффиксом;
- JWT-аутентификация пока не используется;
- для production понадобятся PostgreSQL, Redis/WebSocket broker, полноценные миграции и секретный менеджер.
