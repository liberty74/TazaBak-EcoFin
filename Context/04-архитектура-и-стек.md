## Железо — две платы, а не четыре

**Важно для презентации.** В текущем EcoFin-репозитории собран контур из двух
плат:

### 1. ESP32 DevKit — муниципальный бак

- `HC-SR04` меряет расстояние до поверхности мусора → заполненность
- `DS18B20` меряет температуру внутри бака → пожарный риск
- `SG90` закрывает и открывает заслонку по команде backend
- Связь: HTTP POST телеметрии каждые 15 секунд + постоянный WebSocket для
  команд

Прошивка: [`firmware/municipal_esp32/municipal_esp32.ino`](../firmware/municipal_esp32/municipal_esp32.ino).
Один флаг `TAZABAK_CLOUD` переключает плату между локальным стендом и облаком:
адрес, порт и TLS подставляются сами, поэтому указать HTTP на 443 невозможно.

### 2. ESP32-CAM — компьютерное зрение площадки

- Отдаёт MJPEG-поток и одиночные кадры
- Backend забирает кадр и прогоняет через YOLOv8 → алерт о навале мусора
- Диспетчер видит кадр с рамками обнаруженных объектов

**Raspberry Pi 4 и Arduino Uno в этом проекте не используются.** Они были в
предыдущей версии проекта (сортировка хлеба двумя заслонками по QR). В
EcoFin-репозитории их прошивок нет, и показывать их на слайдах нельзя: на Q&A
попросят показать код, а его нет.

## Как устроена доставка команд

Команда устройству не теряется, даже если плата в этот момент офлайн:

1. Backend записывает команду в таблицу `DeviceCommand` со статусом `PENDING`
2. Пытается отправить её через WebSocket
3. Плата подтверждает получение (`COMMAND_ACK`) — статус меняется
4. Нет подтверждения — команда остаётся в очереди и уходит при следующем
   подключении

Повторный запрос с тем же ключом идемпотентности не создаёт дубль — возвращает
ту же команду.

**Пожарный interlock:** при риске возгорания устаревшие `OPEN_LID` отменяются,
а `CLOSE_LID` имеет приоритет. Заслонка не может открыться, пока бак горячий.

## Главные API-потоки

| Поток | Endpoint | Что происходит |
|---|---|---|
| Хлеб | `POST /api/bio/analyze` | Фото → CLIP → approve/reject/invalid → QR → баллы |
| Телеметрия | `POST /api/sensors/ingest` | distance/temp → EMA заполненности → FireScore → тревога → CLOSE_LID |
| Камера | `POST /api/vision/frame` | Кадр ESP32-CAM → YOLOv8 → алерт ILLEGAL_DUMP |
| Диспетчер | `GET /api/dispatch/summary` | Нерешённые тревоги, приоритеты, команды |
| Устройство | `WS /ws/device/{device_id}` | Канал команд OPEN_LID / CLOSE_LID с ACK и повтором |
| Экономия | `GET /api/eco/savings` | Расчёт сэкономленных рейсов, топлива, CO₂, тенге, окупаемости |
| Выручка | `GET /api/eco/revenue` | Потоки дохода пилота и проекция на масштаб |
| Прогноз | `GET /api/eco/business/forecast` | Прогноз списаний пекарни на завтра |
| Маршрут | `GET /api/eco/route` | Маршрут по фактической заполненности |
| Советы | `GET /api/eco/recommendations` | Три действия на завтра от grounded-LLM |

## Экраны

**Житель:** главная, карта контейнеров, сканирование хлеба, профиль и баллы,
магазин наград и Eco-NFT, сообщество, рейтинг, чат с Баки AI, настройки.

**Диспетчер:** дашборд, тревоги, устройства IoT, карта, маршрут, экономия,
выручка, прогноз, кабинет пекарни, задания волонтёрам.

## Надёжность

- SQLite на локальном стенде работает в режиме WAL, с внешними ключами и
  busy timeout
- Баллы фиксируются журналом `PointTransaction`, поэтому баланс всегда можно
  сверить по начислениям и списаниям, а не хранить одним числом
- Миграции дополняют схему без потери данных и одинаково работают на SQLite и
  PostgreSQL — проверка схемы идёт через SQLAlchemy, а не через `PRAGMA`
- 132 автоматических теста на backend, отдельные тесты на frontend

## Что работает без интернета и внешних сервисов

- Анализ хлеба локально через CLIP (в облаке — через Gemini, потому что
  бесплатный инстанс даёт 512 МБ и torch туда не помещается)
- Все расчёты экономики
- Приём телеметрии и управление заслонкой
- Рекомендации: если Gemini недоступен, они собираются детерминированными
  правилами по тем же числам — меняется формулировка, но не цифры
